# Project Governance: TouchDesigner Audio-Reactive Mesh

This document outlines the governance model and decision-making process for `touchdesigner-audio-reactive-mesh`. Explicit governance ensures clarity for contributors regarding how decisions, feature approvals, and project directions are handled.

---

## 1. Governance Model

This project operates under a **Benevolent Dictator For Life (BDFL)** model.

* **Lead Maintainer / BDFL**: Mariam Anbar ([@mariamanbar](https://github.com/mariamanbar)).

As the founder and project lead, the BDFL holds final decision-making authority on the technical vision, network architecture, and release milestones of the project.

---

## 2. Decision-Making Process

While final decisions rest with the BDFL, community participation and open discussions are actively encouraged\:

* **Proposals & Features**: Anyone can propose a feature, bug fix, or network optimization by opening a GitHub Issue.
* **Public Discussion**: Design and technical discussions occur openly within GitHub Issues and Pull Request comments.
* **Final Authority**: The BDFL makes final calls on whether proposed features align with the project's goals (e.g., performance targets, visual stability, and clean node architecture).

---

## 3. Roles & Responsibilities

### Lead Maintainer (BDFL)
* Defines the project roadmap, core pipelines decisions, and major releases.
* Conducts reviews and approves or closes incoming Pull Requests.
* Maintains community standards, repository hygiene, and security policy enforcement.

### Contributors
* Anyone who submits bug reports, feature suggestions, code/network updates, or documentation fixes.
* Adhere to the [Code of Conduct](https://github.com/mariamanbar/touchdesigner-audio-reactive-mesh/blob/main/.github/CODE_OF_CONDUCT.md) and [Contributing Guidelines](https://github.com/mariamanbar/touchdesigner-audio-reactive-mesh/blob/main/.github/CONTRIBUTING.md).

---

## 4. Conflict Resolution & Boundary Setting

If a disagreement arises regarding network structure, visual direction, or proposed features:

1. **Discussion**: The rationale for both sides will be discussed in the relevant GitHub Issue or PR thread.
2. **Final Call**: The BDFL evaluates the trade-offs (e.g., feature value vs. performance impact) and renders a final decision.
3. **Alternative Options**: If a proposed direction is not merged because it falls outside the main roadmap, contributors are always welcome to fork the project under the terms of the MIT License.

---

## 5. Future Governance Evolution

As the repository grows and active long-term maintainers join, this governance structure may transition toward a **do-ocracy** or a **steering committee** model. Any adjustments to project governance will be documented in this file.
